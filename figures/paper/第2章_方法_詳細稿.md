# 第2章　方法

## 2.1　基本的考え

### 2.1.1　研究目的とシステムの位置づけ

本研究は，金沢市中心市街地（近江町市場～金沢城～兼六園）において，観光時の暑さに対する**事前計画**を支援する Web システムを構築することを目的とする。具体的には，(1) **クーリングシェルター（以下 CS）** への誘導，(2) **建物による日陰**（直射日射を遮る影）の可視化と経路判断への反映，の二軸で利用者の移動を支援する。

一般に，暑熱環境の評価には平均放射温度（MRT）など，気温・湿度・短波・長波放射のバランスを踏まえた指標が用いられる。一方，MRT を空間的に推定するには，気象観測，表面の反射・放射特性，周辺地物（建物・樹木・地面）の幾何と材質など，多くの入力が必要となる。

本研究では，**都市オープンデータと公開 API だけで再現可能な範囲**を優先した。そのため MRT そのものは算出せず，PLATEAU 建物から求められる **建物影による日陰の有無・分布** を，暑さの強さを表す**簡易的な代理指標**として用いる。すなわち「その地点・経路が，建物によって直射を遮られているか」を示し，経路選択の判断材料の一つとする。

### 2.1.2　モデル上の前提（樹木を含まない）

本研究の日陰モデルは **建物影のみ** を対象とする。街路樹，公園樹，植栽，アーケード，可動式日よけ，雲・大気状態などは**考慮しない**（樹木のない，あるいは樹木の影響を無視した近似である）。

したがって，システムが示す日陰は「**建物由来の影**」に限られる。実際の歩行環境では樹木などが日陰を生じることが多く，実測との比較ではモデルが日向寄りに出やすい（第3章）。本前提は，オープンデータで説明可能な範囲を明示するためのものである。

### 2.1.3　開発の流れ（本章の構成）

日陰・経路機能は，拡張アブストラクト段階の可視化から，計算修正，ナビ統合，時系列データ化，CS 統合へと段階的に拡張した。第2章は次の構成とする。

- **2.2** 建物日陰の導出（拡張アブストラクト前 → 課題 → 改善 → 現行の二モデル）
- **2.3** クーリングシェルター情報（`ジオコーディング/`）
- **2.4** ルート探索（OSM 歩道網，日陰コスト，CS 立ち寄り必須）
- **2.4.1** 参考データ：`金沢城_GPX/`（観光シナリオ・検証用の経路トレース）

## 2.2　建物日影の導出

### 2.2.1　使用データと座標系

| 種別 | データ源 | 用途 |
|------|----------|------|
| 建物 | PLATEAU CityGML（bldg：54366572, 54366573, 54366582, 54366583） | フットプリント，建物高 |
| 地形 | PLATEAU DEM（`*_dem_*_op.gml`） | 検証用幾何影，勾配コスト用標高グリッド |
| 道路（評価） | PLATEAU tran（Road） | 実測比較の評価マスク |
| 道路（経路） | OpenStreetMap（OSMnx） | 歩行ネットワーク |

空間演算は **EPSG:6670**（平面直角座標系第7系）に統一する。緯度・経度（EPSG:6697 / WGS84）からの変換時は，**軸順序**と**ラスタ・画像座標の Y 軸反転**に注意した。

解析域は近江町・兼六園周辺の代表点を基準としたバッファで設定する（`kanazawa_study_bbox()`）。標準グリッドはおおよそ **82×131 セル**，1 辺約 12 m（`compute_summer_shadows.py` の `--resolution`）である。

### 2.2.2　拡張アブストラクト段階（初期システム）

拡張アブストラクト段階では，次を実装した。

1. PLATEAU 建物の **lod0FootPrint** と **measuredHeight** を読み込む。
2. 対象期間 **6月1日～9月30日**，各日 **8～18 時** について太陽位置を求める。
3. 各時刻の日陰分布を **画像（PNG 等）** として可視化する。

影長 \(L\) は，建物高 \(H\) と太陽高度 \(\alpha\) から

\[
L = \frac{H}{\tan \alpha}
\]

とした。影ポリゴンは，建物フットプリントを**太陽方向の逆側**へ平行移動して生成する。太陽ベクトルは方位角・天頂角から ENU（東・北・上）成分 \((s_x, s_y, s_z)\) を構成し，水平移動量は建物高に比例して \((-H s_x / s_z,\,-H s_y / s_z)\) とする（\(s_z > 0\) のとき）。

### 2.2.3　拡張アブストラクト段階の課題（計算面）

初期実装では，次の問題が生じた。

1. **方位角の基準混同**（南基準・北基準）により，影の向きが実態とずれ，**約 180° 反転**する事例があった。
2. **座標変換の不備**（緯経度の軸順，投影 CRS の取り違え）により，影の位置が系統的にずれた。
3. **画像・グリッドへの変換時の Y 軸反転** により，南北が反転して表示された。

これらは「影が出ない」というより，**幾何として誤った方向・位置**に影が描かれる問題であった。

### 2.2.4　改善策（計算の整合性）

上記に対し，次を実施した。

| 項目 | 内容 |
|------|------|
| 太陽位置 | **pvlib** により日本標準時（`Asia/Tokyo`）で算出 |
| 方位角・天頂角 | pvlib の `apparent_zenith`，`azimuth` を採用し，ENU 太陽ベクトルへ統一 |
| 座標 | 建物・影演算を **EPSG:6670** に統一（`plateau_load.py`） |
| 表示 | ラスタ `origin="upper"` と `from_bounds` の対応を統一 |

修正後，影の**方向**および**影長**は \(L=H/\tan\alpha\) と整合する（第3.2節）。本結果は実環境の完全再現ではなく，**計算パイプラインの内部整合性**を示す。

### 2.2.5　拡張アブストラクト後の課題（利用面）と改善

**課題**

- 単一時刻ごとの**画像**であり，Web から任意日時を柔軟に参照しにくい。
- 日陰が**道路ネットワーク・経路探索**と結合されていない。
- ナビ用途に全期間・全時刻をその場計算すると**計算量が過大**。

**改善（フルペーパー段階）**

- `compute_summer_shadows.py` により，**6/1～9/30・毎日 6～18 時**（13 時刻/日）の日陰を事前計算。
- 出力 **`data/summer_shadow_YYYY.npz`**：配列 `masks` の形状 \((T, n_y, n_x)\)，uint8（0/1）。
- 付随 **`summer_shadow_YYYY_meta.json`**：日付範囲，時刻リスト，グリッド範囲，インデックス規則  
  \(t = \text{day\_index} \times n_{\text{hours}} + \text{hour\_index}\)。
- 同一 NPZ に **DEM 補間の標高グリッド `elev_m`** を格納し，経路の**勾配コスト**に利用。

### 2.2.6　日陰モデルの二系統（ナビ用と検証用）

計算コストと精度のトレードオフに対し，日陰を二系統に分離する。

#### （1）ナビゲーション用：平坦地・フットプリント平行移動近似

- 建物を**直方体**（フットプリント + 高さ）とみなし，地盤を**水平**と仮定。
- 各時刻，フットプリントを \((-H s_x/s_z,\,-H s_y/s_z)\) だけ平行移動し，ラスタ化（`one_timestep_mask`）。
- DEM による影の起伏は**省略**（全期間×全時刻の組合わせが巨大なため）。
- Web 表示・経路の日陰率は**原則このモデル**（NPZ）を用いる。

#### （2）検証用：DEM + 幾何影

- `shadow_analysis_kanazawa.py` / `shadow_geometry` 系。
- DEM から地表面を補間し，建物・地形を考慮した**光線・ポリゴン**による日影。
- 精度は高いが計算負荷が大きい。
- `compare_shadow_web_vs_geometry.py` で同一グリッド・同一日時に重ね，日陰の重なり指標 \(I_{\text{shade}}\)（約 0.39）で差を評価する。

### 2.2.7　実測との比較（方法上の位置づけ）

2023年8月5日の歩行トレース（GeoTIFF：青＝日陰，赤＝日向）を正解とし，上記ナビ用モデルと比較する（`compare_field_road_tran.py` 等）。評価は **PLATEAU 道路セル ∩ 実測ラベル有効** に限定する。樹木日陰を含む実測に対し建物影のみのモデルであるため，F1・再現率は低く出ることを**想定内**とする（第3章）。

### 2.3.3　ジオコーディング（国土地理院 AddressSearch API）

`geocode_gsi.py` の手順：

1. `cooling_shelters.csv` を読み込み，各行の **`address`** を取得。
2. **国土地理院 住所検索 API** に GET リクエスト  
   `https://msearch.gsi.go.jp/address-search/AddressSearch?q=<住所>`
3. 応答 JSON の先頭候補 `geometry.coordinates` を **[経度, 緯度]** として取得し，`lat` / `lon` 列に格納。
4. 連続アクセス防止のため **`time.sleep(0.2)`** を挿入。
5. 結果を **`cooling_shelters_geocoded_gsi.csv`** に保存（UTF-8 BOM）。

失敗・候補なしの行は lat/lon を空とし，`csv_to_geojson.py` では**スキップ**する。

### 2.3.4　GeoJSON 化とシステム内部表現

`csv_to_geojson.py` は，lat/lon が有効な行のみ Feature（Point）化する。geometry は GeoJSON 規約どおり **`[lon, lat]`**。

ランタイム（`integrated/cs_spatial.py`）では：

1. GeoJSON を読み込み。
2. **EPSG:4326 → EPSG:6670** に変換（`pyproj.Transformer`）。
3. 各 CS を `CoolingShelterSite`（`cs_id`, 名称, 住所, \(x,y\), `lon,lat`）として保持。
4. **cKDTree** を構築し，最近傍検索・立ち寄り候補の絞り込みに用いる。

## 2.4　ルート探索

### 2.4.1　歩行ネットワークの取得

- **OSMnx**（`osmnx.graph_from_bbox`）で，起点・終点周辺のバッファ（約 **0.008°**）内の **歩行可能ネットワーク**（`network_type="walk"`）を取得。
- グラフを **EPSG:6670** に投影（`ox.project_graph`）。
- 起動時 **`warmup_bbox()`** で研究域周辺のグラフをキャッシュし，初回応答を短縮（`integrated/graph_cache.py`）。

経路の幾何は **OSM 道路中心線** に基づく。PLATEAU tran 道路は**実測評価用**であり，経路グラフそのものではない（2.2.1）。

### 2.4.2　日陰・勾配の辺属性

対象日時の NPZ から `time_index(grid, date, hour)` でマスク \(M\) を取得。

各エッジ（道路区間）について：

1. **日陰率** \(f_{\text{shade}}\)：辺の `LineString` 上を **等間隔 3 点**（統合版。旧 `nav_shadow` は 8 点）でサンプルし，\(M\) の 0/1 の平均をとる。
2. **勾配**：両端ノードの DEM 標高差の絶対値を辺長で除した値 \(| \Delta z | / L\)（標高グリッドが無い場合は 0）。

### 2.4.3　コスト関数（歩行区間）

統合版（`integrated/route_ext.py`）の辺コスト：

\[
\text{nav\_cost} = \varepsilon L + w_d L + w_t \frac{L}{v} + w_s L \cdot |\text{勾配}| + w_{sh} L \cdot f_{\text{shade}}^{\*}
\]

- \(\varepsilon\)：微小項（連結性確保）
- \(L\)：辺長 [m]，\(v\)：歩行速度（既定 **1.2 m/s**）
- 既定重み例：\(w_d=1,\, w_t=1,\, w_s=3,\, w_{sh}=4\)

**日陰項の符号（重要）**

- 統合版 Web UI の **`prefer_shade=True`（既定）** では  
  \(f_{\text{shade}}^{*} = 1 - f_{\text{shade}}\)  
  とし，**日陰が多い辺ほどコストが低い**（日陰を選びやすい）。
- `prefer_shade=False` のときは \(f_{\text{shade}}^{*} = f_{\text{shade}}\)（旧 `nav_shadow` と同型で日陰回避）。

**CS 立ち寄りコスト（必須）**

統合版では **最低 1 か所の CS 立ち寄りが必須**（直行のみは不可）。

\[
C_{\text{dwell}} = w_{\text{cs}} \cdot t_{\text{dwell}}
\]

- 既定：\(w_{\text{cs}} = 2.5\)，\(t_{\text{dwell}} = 600\) s（10 分相当）

### 2.4.4　CS の自動選定と経路合成

1. 全 CS を歩道グラフ上の**最近傍ノード**にスナップ（`get_cs_snap_nodes`）。
2. 自動選定時：起点・終点からの**折り返し距離**が短い CS を **上位 8 件**（不足時 15，30 へ拡大）に絞る（`candidate_visit_cs_indices`）。
3. 各候補について，有向グラフ上で  
   `dist(起点→CS) + dist(CS→終点) + C_dwell` を評価し最小を選択（`single_source_dijkstra` を起点・終点から 2 回）。
4. 選ばれた CS を経由するよう，`起点→CS` と `CS→終点` の最短経路を結合（`networkx`）。

指定 `visit_cs_id` がある場合はその施設を固定する。

### 2.4.5　出力と評価用ベンチマーク

API 応答には，経路座標（6670 および lat/lon），経路長，平均日陰率，CS 名称，各処理時間などを含む。

`integrated/accuracy.py` では，駅～香林坊，兼六園～駅など **5 つの代表 OD** で，CS 候補数・日陰サンプル数を増やした**参照解**との差分を記録できる（高速化の精度トレードオフ）。

### 2.4.6　参考データ：`金沢城_GPX/`

フォルダ **`E:\plateaushade.04.26.27\金沢城_GPX\`**（相対：`金沢城_GPX/`）は，**金沢城公園周辺の観光歩行**を想定した **GPX トラック** の保管場所として設けた。

- **現行の統合ルート API は GPX を直接読み込まない**。経路幾何は OSM 歩道ネットワークから生成する。
- GPX は，(1) 観光シナリオの起点・終点・中間点の設定，(2) 実測・検証用の参照歩行軌跡，(3) 城下町エリアに限定したデモルートの共有，などに用いる**補助データ**とする。
- GPX を利用する場合は，トラックポイント（`wpt` / `trkpt`）の座標系（WGS84）を EPSG:6670 に変換し，OSM 上の最近傍ノードを起点・終点として **`/api/route_latlon`** に渡す運用が想定される。

（フォルダ内の具体的ファイル名は環境により異なる。`.gpx` を配置したうえで，QGIS 等で研究域と重ねて整合を確認する。）
